# synth v0.92 plan: bets against the pulseengine North Star

Status: **draft**. Written 2026-11-20, before v0.91 is tagged. Nothing in this
plan has been built, run on hardware, posted or filed. Every item is a draft;
none claims delivery.

The North Star and its objectives (O1 to O5) are defined in pulseengine.eu's
`data/north-star.toml`. Every item below names the objective it serves. A
`serves:` field for rivet features does not exist in synth yet, so the
objective is stated in each record's text.

The draft scope is recorded as rivet artifacts in
[`artifacts/planning-v0.92-draft.yaml`](../../artifacts/planning-v0.92-draft.yaml).
Why it lives there and not in `artifacts/release-v0.92/` is explained under
[Where the scope is recorded](#where-the-scope-is-recorded).

## Expected headline, stated before the work

**Most O1 rows will read fail at the v0.92 tag.** O1's guard counts a skipped
hardware run as a failure, and the record this plan builds honours it:

| Row | Hardware run expected for 0.92.0 | Expected reading |
|---|---|---|
| `cortex-m4` | None known. gale's earlier silicon evidence on a Cortex-M4 part covers one fixture on an older version | **fail** |
| `cortex-m7dp` (RT1176) | Only if jess runs the tagged image (item D) | fail unless jess runs it |
| `cortex-m0plus` | Only if gale runs `wdg-thin` on its NUCLEO-G031K8 board (item E) | fail unless gale runs it |

There is no rv32 row in this release. The WCET field will hold a number on
`cortex-m4` only and read **absent** on the other two. O1 as a whole stays
`unmeasured` until pulseengine.eu has an indicator script; this release makes
synth's half derivable, nothing more. The value of the release is that these
readings become true, dated and re-runnable, not that they are good.

## Base facts and their age

- synth main is `3dc31524`; the workspace version and newest tag are `0.90.0`.
  **v0.91 is not tagged.** Which release carries the lanes now open or stacked
  is undecided.
- The external measurements this plan leans on are on synth 0.89.0, three
  versions back: jess's silicon run and gale's rv32 driver count. Neither is a
  baseline for 0.92.0 until it is re-measured.
- Unmerged work is named as unmerged: the ARMv6-M i32 lowering and the rv32
  profile work exist only as unmerged branches; pull requests #1749, #1751 and
  #1753 are open.
- The required spec-execution oracle (`scripts/repro/spec_exec_1636_differential.py`,
  wired in `.github/workflows/spec-suite.yml`), read on `3dc31524`: it compiles
  a self-contained image per spec file, loads the ELF's `PT_LOAD` segments into
  the emulator and executes each directive against wasmtime. Legs: `cortex-m4`
  (executed floor 11634) and `cortex-m7dp` (floor 24087), of 57588 directives
  in the pinned suite. Its known-failing table holds 27 entries per leg, all
  under the `#539-grow-fails` envelope label. **It sets the emulator's CPU
  model to the permissive "max" core on both legs, not to a Cortex-M4.**

## Item A. Wrong code, with a number (`RQ-92-WRONGCODE`)

**Serves O1** (`execution_match`). A wrong value on any covered target makes
that number false.

**Indicator change.** The `execution_match` wrong count on the rows this release
publishes is zero outside declared pins, and the count of **live** open
wrong-code issues falls.

**Step 1, first week: a measured census.** For every open issue that reports
wrong output with exit 0, one row: issue, backend and flags, repro input, the
oracle command, and the result on a named main commit: `live`,
`fixed-unreleased`, `not-reproduced` or `no-oracle`. A title scan of the open
list on 2026-11-20 gives about 29 candidates, among them Refs #1745, #1747,
#1752, #1568, #1604, #1672, #1676, #1684, #1696, #1698, #1699, #1710, #1711,
#1712, #1713, #1714, #1715, #1716, #1717, #1720, #1721, #1205, #1210, #1214 and
#1241. **That scan is not the census**, and how many of them are live is
unknown. Where an existing pin table already pins the wrong value, a passing pin
run is the evidence that the defect is live; no second harness is written.

**synth can close alone.**

- The census is a generated file with one executed oracle result per row,
  produced by one command and re-run at the tag.
- The count of `live` at the tag is at most half the census count, and
  **zero live on Thumb-2 `cortex-m4` with default flags**.
- Every fix lands with an oracle that was red on its base commit and is green
  on the fix, both runs recorded.
- Issues found during the release are added to the census and counted.

**Kill.** The item failed if the census cannot be built (more than a quarter of
the rows end `no-oracle` or `not-reproduced`), or if the live count at the tag
is higher than at the census, new finds included. Recent lanes have found
previously unknown miscompiles while working on known ones, so the second kill
is a real possibility; if it fires, the release notes lead with it.

**Size and risk.** Large; the largest item in the release. The count is not
under synth's control once new oracles start finding things.

## Item B. A thin target record (`RQ-92-TARGETRECORD`)

**Serves O1.** It makes synth's half of the indicator derivable.

**Indicator change.** For `cortex-m4` and `cortex-m7dp`, version 0.92.0, these
fields in one file, never summed:

- `reach`: functions accepted over functions in the corpus, with the corpus
  named. In this release the corpus is the vendored spec suite plus the
  repository's own fixtures. **The record states beside the number that the
  corpus was chosen by the project and is not a consumer's.**
- `execution_match`, on the shipped ELF (the self-contained image, segments
  loaded as linked): executed, matching, wrong and pinned counts, each its own
  number.
- `wcet`: a bound coverage figure where a sound model exists (`cortex-m4`);
  otherwise the field is **absent**. A decline reason is not a number and does
  not render as one.
- `hardware_run`: a run reference bound to an image digest, or `none`, which
  renders as fail.

The `cortex-m0plus` row is added by item E and labelled **code-level, not
ELF-level**, because that target has no self-contained image; under this record
a code-level row does not satisfy `execution_match`.

**What is built.** A small Rust assembler that reads the JSON the existing
required oracles already emit and writes `target-record.json`. No new execution
suite, no consumer corpus, no per-ABI link step, no ladder rung, and no
translation-validation share anywhere.

**synth can close alone.**

- One command produces the record from a clean checkout; the file is a release
  asset listed in the signed checksum manifest.
- An **executed-vector floor per target**, set to the measured count and never
  lowered to make a run green. A row with zero executed vectors fails, even
  with zero wrong.
- Three negative controls in CI: an empty or unfetchable corpus fails instead
  of producing an empty row; a planted wrong instruction in a fixture image
  makes the wrong count non-zero and the job red; removing a hardware reference
  turns the row to fail.

**Signing and re-check.** The record goes into the release's checksum manifest,
which the release workflow already signs and attests. The corpus for these rows
is the public spec suite at a pinned commit, so an outside party can re-run the
record without any consumer module.

**Cadence.** The North Star posts at each monthly layer, and a release tag is
not a layer. The record is produced at the tag and regenerated on main by a
scheduled job for each monthly layer (first: 2026.12), keyed by version and
commit. A layer with no new release repeats the last tagged record with a new
measurement date.

**Kill.** The record cannot be regenerated on the tag from a clean checkout, or
a row can pass with nothing executed. Wrong if the assembler ends up
duplicating oracle logic instead of reading oracle output.

**Size and risk.** Small to medium; risk low.

## Item C. cortex-m4 `execution_match` on a Cortex-M4 model (`RQ-92-M4EXEC`)

**Serves O1.** `cortex-m4` is the only L1 target and the only row with a WCET
number. Refs #1636.

**Indicator change.** `execution_match` for `cortex-m4`, version 0.92.0,
measured on a Cortex-M4 CPU model on the shipped image: executed count above
today's floor of 11634, wrong count zero, pinned known failures at or below 27.

**What is done.**

1. Run the required `cortex-m4` leg on the emulator's Cortex-M4 model, read
   back and asserted, instead of the permissive "max" core. An instruction a
   Cortex-M4 cannot execute then fails the directive instead of passing.
2. Raise the executed count by fixing declines that keep whole spec files from
   executing, taken from the leg's own per-file accounting.
3. Work the 27 pinned `memory.grow` entries: each either passes or stays pinned
   with its reason.

**synth can close alone.**

- The leg passes on the Cortex-M4 model in the required check, and a planted
  Thumb-2 instruction outside the M4's set fails it.
- The executed floor is strictly above 11634. **The size of the rise is not
  promised here**: it is set after step 1, because switching the model may move
  the count in either direction.
- Wrong count zero; pinned count does not rise.

**Kill.** If the model switch shows that directives passed only on the
permissive core, that is a finding to publish, and the floor is reset to the
true count; the item has then paid for itself. It failed if the floor at the
tag is at or below 11634 on the M4 model with no such finding to explain it.

**Size and risk.** Medium; risk low to medium.

## Item D. RT1176: bind a silicon run to the tagged compiler (`RQ-92-RT1176DIGEST`)

**Serves O1**, the `hardware_run` and `execution_match` fields of `cortex-m7dp`.

**Stated plainly.** jess's existing result is a draft, manual record on synth
0.89.0: one completed run per image, loaded to RAM over SWD, with resets of
unknown cause reported. It is on-target execution match. It is none of the three
rungs O1 names for jess (HIL against the relay simulation, real drone, flight),
and it is not a flash-booted image. It moves synth's half once.

**synth's three items.**

1. A CI job that builds the estimator image from pinned inputs and produces a
   word capture in jess's capture format, judged by jess's judge.
2. A byte-identical image across **two hosts of different operating system and
   architecture**.
3. A release candidate with a published digest, and a rule: **the image built
   by the tagged 0.92.0 compiler has the same sha256 as the image that ran on
   silicon.** If a later change moves that digest, the run no longer counts for
   0.92.0 and the row reads fail.

Item 3 freezes code generation for this image from candidate to tag. Item E's
lanes may land in that window only because each is gated on byte identity for
every non-ARMv6-M target; the digest check enforces it.

**synth can close alone.**

- The capture job is green on the candidate; the judge exits 0 on its capture;
  a perturbed-input control yields a different fold.
- `shasum -a 256` of the image is equal across the two hosts, and equal between
  candidate and tag.
- The record's `cortex-m7dp` row carries the image digest.

**Cross-repo outcome, not part of acceptance.** jess runs that digest on the
RT1176: 5 of 5 consecutive loads complete and the judge passes. There is no
written-explanation alternative. If it does not happen, the row reads fail and
the release notes say so.

**Kill.** Not bit-exact on silicon; or the digests differ across hosts and
cannot be made equal; or the candidate-to-tag digest moves and no re-run
happens.

**Size and risk.** Small to medium in synth. Risk high on the cross-repo
outcome: one bench, unexplained resets, and a result on an old version.

## Item E. cortex-m0plus: gale's `wdg-thin`, whole (`RQ-92-WDGTHIN`)

**Serves O1**, a new target row. Refs #1301.

**Indicator change, in one unit.** `reach` for `cortex-m0plus` over the
functions of gale's `wdg-thin` (31, by gale's count): from the count measured
on main at the start of the lane (not measured for this plan) to all of them.
`execution_match` is code-level, with calls resolved by the oracle's own link
step, and labelled as such. `wcet` is absent. A support-level promotion may
follow through the existing gate; it is a by-product, not the indicator.

**Lanes for this release only.** All direct calls, internal and import. The
ARMv6-M register pool, scratch and frames. 16-bit literal pools, only if
`wdg-thin` needs them. `br_table` (the module has one). **Not in this release:**
i64, linear memory and globals, wohl's door engine, the M0 cycle table.

**synth can close alone.**

- `synth compile gust_wdg_thin.loom.wasm --target cortex-m0plus --relocatable
  --all-exports` exits 0 with no export skipped, and every byte of `.text`
  decodes as ARMv6-M.
- On the emulator's Cortex-M0 model, read back: the sequence of MMIO writes for
  each scripted scenario equals the reference engine's (unlock, start,
  refresh). The scenarios are enumerated from the module's exports, not a fixed
  vector count.
- Every non-ARMv6-M configuration compiles to identical bytes before and after
  each lane, with the potency control.
- The embedder check rejects a boot shim that sets the memory-base register
  with the ARMv7-M encoding.

**Cross-repo outcome, not part of acceptance.** gale records its two-boot
watchdog row on the NUCLEO-G031K8 with an image built by synth 0.92.0.

**Kill.** `wdg-thin` cannot be lowered whole within ARMv6-M's branch and literal
reach without declining a function; or a byte moves on another target without
an oracle proving the new bytes correct.

**Conflict to resolve before committing.** wohl's draft plan for its next
release (unmerged) includes a door image built by synth for ARMv6-M, booted
under emulation, with a hard-date kill if synth's lane is not merged three weeks
before wohl's tag. Leaving the door engine to synth's following release fires
that kill unless the dates align. This is the owner's call; the ask is listed
below.

**Size and risk.** Large. Risk high in the pool and frame lane, which
parametrises a register set every ARM path shares.

## Conditional item. The kernel axiom audit (`RQ-92-AXIOMAUDIT`)

**Serves O3** (Every verified claim is backed). Kept only if O3's guard can hold
as written: ledger entries may only shrink, with **no growth waiver**.

**The probe that decides, one day, before any commitment.** Run
`Print Assumptions` over every theorem in the proof suite and take the set of
distinct axioms reached. Check that the output is identical across two
toolchain patch versions, and that no lane planned for v0.92 or v0.93 adds a
Rocq axiom or parameter.

- If both hold: ship the audit in the required proof check against a committed
  list, with a planted-axiom control, and delete the text-pattern axiom pins it
  replaces. The other assumption classes (rule side conditions, atomic model
  steps, validator preconditions) are **named in the ledger as uncounted**. An
  undercounted first baseline is the known weakness: the list is its own
  starting point.
- If either fails: **deferred.** A planned rv32 instruction-set model is the
  likely reason, since a new model usually brings parameters, and under this
  guard that growth has no legal path.

This item adds no proof and fixes no defect. O3 stays `unmeasured` until
pulseengine.eu has an indicator script.

## The O2 question, asked instead of assumed

The quarter's only committed North Star target is O2: one wohl release with the
full bundle, verified by one command. synth is not a consumer, but two things
say the question should be asked rather than dismissed:

- wohl's draft plan wants a **signed, synth-built image** as a release asset in
  its bundle.
- An evidence bundle that contains compiled code is only re-checkable if the
  compiler that produced it is identified.

**Ask to wohl:** does the bundle need, from each synth release, (a) an attested
compiler binary with a digest the bundle can cite, (b) the target record for the
target it ships on, (c) a compile provenance record per image? synth's release
already signs its checksum manifest and emits build provenance; whether that
form is what the bundle's verify command can consume is unknown.

## A named, open gap: WCET on the flight target

The row jess flies on is a Cortex-M7. synth's WCET rule is strict and there is
no sound cycle model for a cached, dual-issue core, so **that row's WCET number
will read absent for as long as both stay true.** This is a gap in O1, not a
scoping choice. It needs an owner decision among: state it on the North Star
page as absent for this target; fund a sound model for a restricted
configuration (whether one exists for this core is not established); or report
a measured figure under a different name that never appears in the WCET field.

## Next (v0.93), not this release

- wohl's door engine on `cortex-m0plus`: i64, linear memory and globals through
  the base-register copy, then L2.
- rv32 for the esp32-c3: the declared-profile fix, a re-measurement of gale's
  driver set on a current version, and an execution leg in which **driver
  exports execute and equal the reference**. Two different driver sets have
  been cited (15 thin drivers and 11 cross-compiled drivers); they must be
  reconciled first.
- The M0 and M0+ cycle table, after the timing figures are read from the
  reference manuals instead of recalled.
- The full trust-escape ledger, if a legal path for a new model's parameters
  exists under O3's guard.
- A consumer corpus for `reach`, once the digests asked for above exist.
- The Thumb-2 acceptance-ladder rung, once its corpus is reachable from CI.

## Not doing, and why

- **x86-64 past the skeleton:** no O1 indicator moves.
- **A translation-validation share:** forbidden by O1's guard until
  whole-function validation exists.
- **cortex-m33, SIMD, rv64, Rocq models for rv32 and aarch64:** no consumer or
  no capacity this period.
- **O5:** it is not established that a synth gate can run as a signed component
  under kiln with the required equivalence test.
- **O4:** nothing synth-specific.
- **Release-machinery issues:** worked only when one blocks an item.
- **Attributing the bench resets:** open-ended debugging with no bound; dropped
  from item D.

## Order and capacity

1. Item A's census, week one. Its count sets A's target.
2. Items B and C, which read the same oracle.
3. Item E's lanes, in sequence.
4. Item D's candidate at least two weeks before the tag.

CI holds three pull requests at a time. Five items is the ceiling. **If one must
go, it is item E's literal-pool lane, then the conditional item. Item A is never
the one cut.**

## Where the scope is recorded

While `ANCHOR_TAG` is `v0.90.0`, the release being cut is v0.91, and two gates
refuse a v0.92 record they can see. Both refusals were reproduced on `3dc31524`
before this plan was committed:

- `scripts/status_evidence_check.py`, CENSUS: a file under
  `artifacts/release-v0.92/` makes the cut read as v0.92 against the expected
  v0.91, and the check fails.
- `scripts/recurring_na_filing_check.py`: a `release: v0.92` field on any
  artifact under `artifacts/`, topic files included, makes the tree's maximum
  release v0.92 against anchor+1 = v0.91, and the check refuses.

So the draft records live in a topic file, `artifacts/planning-v0.92-draft.yaml`,
with no `release:` field and `status: draft`. The file name carries the version,
which dates its records for the unscoped-artifact rules. No record is in any
release's close set. When v0.91 ships, the v0.92 planning pull request moves
each surviving record into `artifacts/release-v0.92/`, adds `release: v0.92`,
`issue-scope` and `done-when`, runs each refuting command, moves the anchor to
`v0.91.0`, and deletes the topic file.
