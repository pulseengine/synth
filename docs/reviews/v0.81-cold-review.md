**Commit reviewed:** `574a69c3`

Round 1 ran TWO independent reviewers over the release candidate with DISJOINT
mandates — one on the prose and the numbers, one on the code and gate potency —
each given no inherited framing and told explicitly not to trust any narrative,
comment or docstring. Round 2 ran two more, briefed to **ATTACK round 1's
corrections**, because v0.80's round 2 found SEVEN defects introduced by round 1's
sixteen fixes, three of them a sentence corrected where the reviewer quoted it and
left standing where it lives.

**Round 1: 31 findings. Round 2: 20. Fifty-one in total**, and the great majority
were defects in this release's own work rather than in inherited code.

The declared commit is `574a69c3` because it is on main's FIRST-PARENT LINE. The
corrections live on a branch that squash-merges, and a squash commit has no parent
link to the branch it came from — so a branch tip could never be an ancestor of the
release commit. What each round examined is stated per round below.

## Round 1, mandate A — prose and numbers (18 findings)

**The two that carried a lane's verdict.** `RQ-81-WIDEFILE4` asserted that "every
`<< 7` in that file is an A32 shift-immediate, a different encoding class". FALSE
and self-refuting: 43 lines in `arm_encoder.rs` contain `<< 7`, at least NINE are
VFP register fields (`:7617` is literally `(n << 7) | (m << 5)`), and the artifact's
own description already conceded that for a THREE-register op bit 7 IS the N
qualifier. The claim the argument actually needs — that all three 2-register
`VMOV.F32` emitters and the shared `encode_vfp_2reg` leave bit 7 untouched — holds.

Worse, the same artifact claimed the sole scalar-f32 `VABS` emitter is the
`F32Copysign` expansion. `0xEEB00AC0` has **THREE** emitters: `:1992` and `:6322`,
both lowering `ArmOp::F32Abs` on two different encoder paths, plus `:7310` in
copysign. And the fixture contains ZERO `f32.abs`, ZERO `f32.copysign` and ZERO
`f32.neg` against 130 `f32.mul` operators — so NONE of the three should be
reachable. **"Three candidates become one" was WITHDRAWN.** This programme's own
memory for #1439 had warned "copysign may not be reached at all; do not assume it
is", and the artifact asserted it anyway.

**The closure arming, found independently by the reviewer and by the operator.**
Two artifacts were set `status: implemented` for one reason — to stop R3 reporting
that a `proposed` status under-reports work whose done-when evidence exists. A
CLAIMING status is also exactly what `authorised_close_set` reads as permission to
close. So satisfying one gate silently entitled the release to close an external
reporter's live defect and a defect whose cause is not named. Neither gate is
wrong; nothing read their conjunction. Resolved with `issue-scope: outlives`, which
R12 validates ONLY beside a claiming status — so the status had to stay and the
scope had to be declared separately. Authorised went from 6 to 4, with 2 held open.

That one also demonstrates why attribution is derived from the BODY PREFIX: the
external defect's `author.login` is `avrabe`, which reads as internal under every
author-based filter; only the `**[jess]` prefix shows otherwise.

**Numbers that did not reproduce**, each re-derived: a census pair measured before
this release's own eleven artifacts recorded outcomes; an authorised count quoted as
an invariant when it is not; `ci.yml` line pairs correct at v0.80.0 and stale here;
"five live `sh()` sites" when there are six, the omitted one being the very site the
description discussed; "ten callers" when nine are live; a `539` that is
`ANCHOR_PROGRAMME` at the v0.80.0 anchor against a live count of 550; "the
reporter's four" prefixed comments when three of the last six carry a prefix and one
carries none.

**Two internal contradictions.** `RQ-81-PAGESIZE3` re-adopted a ">= 32 B power of
two" page scoping that its OWN description calls spec-invalid — gale's >= 32 B is
the ARMv7-M PMSA REGION granularity the embedder programs, and

**`_release.yaml` carried statistics against its own stated rule.** Both removed.

Round 2 existed because last release's round 2 found seven defects in sixteen
fixes. It found twenty in thirty-one.

pinned v0.78's six failing values BY VALUE using `v not in VALS` — and `-0.0 == 0.0`

### The tag guards, hand-checked and negative-controlled on live data

Written out as `tag_guards.sh` and validated in THREE directions rather than
read:

- **On v0.80.0's merge commit** (`2799b04d`, a known-good tag): 88 check-runs
  derived, 9/9 required SUCCESS, none cancelled/timed_out, all completed, and W2b
  correctly REFUSES because HEAD is elsewhere. rc=1.
- **On HEAD** (`7bff4a2d`): all guards pass, 72 check-runs, rc=0.
- **On an in-flight commit** (`e73db764`, #1482's head mid-run): **W3b reported
  "all 9 required contexts are SUCCESS" while W3c REFUSED on 9 incomplete
  check-runs — one of them the MC/DC run.** rc=1.

That third case reproduces, on live data, the exact hole v0.80 found in its own
guard script: `tag_release.sh` GATE1 step 5 depends on the MC/DC run, which is
**not** one of the nine required contexts, so a guard that only checks the nine
would have said "safe to tag" with MC/DC still `in_progress`. W3b alone is a pass
about the wrong subject; W3c is what makes the pair sound.

**And the measurement nearly lied about itself.** The first run reported
`GUARDS: REFUSED` beside `rc=0`, because `$?` after `script | sed` is **sed's**
exit code. Re-measured without the pipe: rc=1 on a refusal, rc=0 on HEAD. In a
tag guard that is the difference between refusing and tagging past a refusal.
