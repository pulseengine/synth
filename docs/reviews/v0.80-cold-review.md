The header spelling above is deliberate and was checked against the checker's own

weaker hex-harvest route for a whole release. Round 2's reviewer B measured the

`declared = None` the harvest returns DERIVED-PASS on whichever cited sha is an
ancestor of the release commit, which can be **the previous release's own release
commit**, labelled "mentions (UNDECLARED, #1161)". The header selects which gate
applies.

## The failure mode, named

**A correction gets written against the site the reviewer quoted, not against the
fact.** Three of round 2's seven (N2, N4, N5) are exactly that: a sentence fixed
where it was cited and left standing where it lives. One (N3) is a right
observation transcribed into a wrong mechanism — the same shape round 1 caught in
RQ-80-ARCHMODEL and congratulated itself for catching, repeated two findings
later. And one defect was introduced by round 2's own correction, caught by a
rule rather than a reviewer: fixing N4 put a statistic into `_release.yaml`,
the one file that MUST CARRY NO STATISTICS.

That is three levels of the same class in one release — a correction, a
correction's correction, and a correction's correction's correction — which is
the honest answer to "is the correction process safe?". It is not safe; it is
*audited*, and the audit is what makes it survivable.

## Reviewer independence

Three fresh-context agents, no inherited framing, each given the git ref and told
to read at it. Round 1's two had disjoint mandates and did not see each other's
output. Round 2 was given both round 1 reports and the correction diff, and its
brief was explicitly to attack them. All mutation testing was done on COPIES; the
repository working tree was verified clean at the start and end of each round.
