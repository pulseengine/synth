### Finding 16 — REFUTED, and how

The claim: with `spill_area_reserved == false` and `spill_base` Some, the i64
area is not recorded, so a slot handed out at `i64_spill_base` — the region that
aliases the #204 param homes, the original #331 shape — would be **unpoliced**,
a class the validator caught before #1321.

The state is unreachable. All **eight** non-test `spill.alloc()` sites are
dominated by a guard:

There are **five** non-test `spill.alloc()` call sites, all in
`instruction_selector.rs` — `:1104`, `:3243`, `:4033`, `:8473`, `:8657` — and
each is dominated by a guard, at **eight** distinct guard sites. The two counts
differ because three of the five allocators are helpers reached from more than
one guarded caller.

- `instruction_selector.rs:8461` (arg-move cycles) and `:8650` (call-result
  parking) test `spill.area_reserved` directly and return the ladder-recoverable
  exhaustion `Err`, immediately above `:8473` and `:8657`.
- `:1076` gates `spill_deepest_reg` on `spill_on_exhaustion` by a
  **short-circuiting `||`**; `:3392` and `:5479` gate
  `alloc_vfp_local_frame_slot` on `vfp_frame_home_locals`;
  `select_with_stack.rs:884` and `:4936` gate the callers of
  `vfp_reload_spilled`/`vfp_ensure_headroom`, which own `:4033`, on
  `vfp_spill_on_exhaustion`. Every one of those rungs **implies** the area,
  because `select_with_stack.rs:296` passes exactly that three-way disjunction as
  `force_spill_area`, and `has_i64` ORs it in.
- `instruction_selector.rs:1867`, the other caller of `spill_deepest_reg` inside
  `alloc_consecutive_pair`, is reached only by i64 pair allocation, which implies
  `has_i64` by the same derivation.

> Pass 1 wrote this as "all **eight** non-test `spill.alloc()` sites", evidenced
> with eight line numbers **none of which is an allocation line**, and with a bare
> `:1867` placed after two `select_with_stack.rs:` citations although it belongs to
> `instruction_selector.rs`. Pass 2 re-derived every caller set independently and
> agreed the narrowing is sound — the substance held, the citation did not.

That last one rests on an invariant rather than a check, so it was **measured**:
an `assert!(self.area_reserved, …)` planted in `SpillState::alloc` fired **zero**
times across the 766-test `synth-synthesis` suite and the corpus sweep's 175
compiled modules / 3428 executed vectors. A `#[should_panic]` control in the same
build confirmed the assert **does** fire when `alloc` is reached unreserved — so
the zero is evidence, not a dead probe. The probe was reverted and the source
sha256 restored byte-identical; it is not in the shipped tree.

### Finding 14 — recorded, deliberately not back-filled

v0.70 is the **first release since v0.61 with no `_release.yaml`**; the plan PR
#1336 omitted it, which is why v0.69 ships 10 files under its release directory
and v0.70 ships 9.

It is **not** created here. The file is a *plan-time* document — v0.69's reads
"EVERY ARTIFACT HERE WAS VERIFIED AGAINST SOURCE ON v0.68.0 **BEFORE IT WAS
WRITTEN**" and closes with "HONEST RISKS, recorded before the work". Authoring
that at the tag manufactures a plan-time record, in a release about evidence you
can re-derive. No gate reads it either: `status_evidence_check.py`'s R0 constrains
the file only **if present** (it must parse, and must be comments-only, because a
keyed `_release.yaml` is skipped silently by rivet). Its absence is invisible.

So the gap is named here with its date and cause, and **v0.71's planning PR
creates `artifacts/release-v0.71/_release.yaml`** — at plan time, where it belongs.

### Finding 17 — recorded, deferred, with the measurement

`arm_backend.rs:2232-2249` asserts the frame is unchanged with
`arm_instrs.iter().any(|ins| Sub{SP,SP,Imm(n)} if n == frame_size)` — **any** such
instruction, not the prologue's. It is safe today: the only `rd: Reg::SP` `Sub` in
`select_with_stack.rs` is line 330, and every other SP write is an `Add`. Equal
`frame_size` implies unchanged areas only because both derive from the same
`layout`. That is a true statement about today's emitter, not a structural tie, and
a second SP-decrementing site would make the self-check pass vacuously. Deferred
rather than changed at a release cut, because tightening a self-check on the
shipped codegen path needs its own oracle and its own red-first case.

### The shared root cause, in the reviewer's words

> Findings **3, 5 and 6** are one mechanism, not three coincidences: **a number
> measured before the last edit to the thing it measures.**

`41 total` was written by the hunk that added two lines to that file; `5243` was
measured on the parent and published beside `7242` from the cut; `34 → 39` was
right at the parent and made `40` by this release's own finding-18 test. In a
release titled *"Evidence you can re-derive"*, **the last commit invalidated three
of its own published figures and nothing re-derived them.**

The durable lesson is narrower than "re-measure everything": a figure that counts
the artefact it is written in, or that pairs a before with an after, cannot be
taken on the tree where it was drafted. The `.wat` header stopped quoting its own
total for exactly this reason — correcting it in place made it wrong a second
time, in the same session.
