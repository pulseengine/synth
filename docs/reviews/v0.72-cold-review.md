## THE BLOCKER: a shipped silent miscompile in a MUST lane

**RQ-72-ISLANDS traded a loud refusal for a silent wrong answer on the shipped
default path** — the exact inversion this project exists to prevent, in the lane
whose own stated rule is *"a deletion or motion that moves bytes without an
oracle proving the new bytes correct is REFUSED, not explained"*.

`resolve_label_branches` (`arm_backend.rs:1708`) rewrites every local branch to a
BYTE-ACCURATE offset, and `validate_branch_targets` (1712) gates each target onto
the instruction-start set. The inline island is inserted at **1840**, inside the
encode loop — *after both*. Inserting bytes at a point a branch straddles moves
the target without moving the branch.

Reproduced independently of the reviewer, on a fixture with one forward `br_if`
spanning the island:

```
island         0x100c .. 0x1014               = 8 bytes
branch target  emitted 0x26ba, correct 0x26c2 = 8 bytes early
26ba: str.w r0, [sp, #0x8]    <- clobbers local 2 (i64 lo)
26be: str.w r1, [sp, #0xc]    <- clobbers local 2 (i64 hi)
```

The shortfall **equals the island size exactly**. The taken branch writes the
last filler `i64.mul` into the very local it was supposed to skip. Islands off:
the same module REFUSES (`imm12=9920 > 4095`). Islands on: it compiles and is
wrong.

**Why no oracle saw it.** `litpool_islands_345.wat` has ZERO control-flow ops
(`grep -cE '\(if|\(block|\(loop|br_if|\(br '` → 0), and the differential's
byte-identity leg only compares modules that need NO island. The artifact's
`verified-by` calls that byte-identity "the negative control" — but the affected
modules are precisely the ones that previously REFUSED, so they have no byte
baseline to be identical to. **The control could not cover the class by
construction.**

**The fix is deliberately conservative.** `label_branch_spans()` computes each
resolved branch's span; the placer refuses any insertion point that separates a
branch from its target, falling through to the end-of-function pool where #345's
out-of-range error fires — the loud v0.71 behaviour. Doing it properly means
resolving branch offsets and island placement in ONE fixed point (LLVM's
ARMConstantIslandPass shape), which is a real pass needing its own execution
oracle; inventing it at a release cut is how this shipped in the first place.
That is filed, with the fixture already committed.

Confined, by the lane's own differential: `165 byte-identical, 0 MOVED`,
`6/6 args bit-exact vs wasmtime`. `litpool_islands_345_branchspan.wat` is
committed and asserted to refuse on BOTH legs.

## Gate potency — the two questions, asked of every gate

### A pin that could not fail, in the lane about gates nobody asks

RQ-72-ISSUEGATE deliverable (c) pinned the `issue-scope:` census line with
`[0-9]+` on the authorised count, and the artifact said *"Verified the pattern
MATCHES the live output rather than merely existing — a pin that never matches
is worse than none."* Every word true, and only ONE of the two questions:

```
echo 'issue-scope: v0.72 — 0 issue(s) authorised ...' \
  | grep -qE '^issue-scope: v[0-9]+\.[0-9]+ — [0-9]+ issue\(s\) authorised'   -> MATCHES
```

The pin passed on exactly the vacuous census it was added to catch. v0.71
shipped the mirror failure — a musl gate that could never PASS — one release
earlier.

**The naive repair is also wrong, and measuring says so.** `[1-9][0-9]*` is the
shape the 17 sibling pins use, but zero authorised is the LEGITIMATE plan-time
state: across v0.72's own history the claiming count went **0** (planning commit
`1e9236d7`) → 1 → 2 → 3 → 4 → 5. That pin would red every future planning PR.
What must never be zero is the POPULATION the close-set was derived OVER — an
empty population and a genuinely empty answer print the same count and mean
opposite things. The line now carries `over N artifact(s)`, N is pinned
`[1-9][0-9]*`, the count keeps `[0-9]+`, and the held-open count is pinned too
(previously unpinned entirely, with RQ-72-ISLANDS' `outlives` on #1331 riding on
it).

### R13 — the class R12 could not see

A `fields:` key one level too high is valid YAML, a real key, and read by
nothing. It breaks no invariant, so NO gate can go red on it. At the v0.71 cut
exactly that happened. Reproduced here, and now caught:

```
issue-scope one level too high ->  held_open {}   authorised {1331, ...}
with R13                       ->  FAIL R13 RQ-72-ISLANDS: `issue-scope:` at TOP LEVEL
```

R13 lives in the LOADER because that is the only place the raw artifact mapping
exists — every consumer downstream sees a flattened tuple in which a mis-nested
key has already vanished. Three tests assert on the DERIVED close-set, not only
the message; disabling R13 fails 5 of them. v0.71's R12 shipped with ZERO tests,
and disabling it left both suites green.

## THE BLOCKER: round 1's island fix had its own blind spot

The guard shipped in #1370 reasons about BRANCH offsets. The same encode loop
records FOUR others from `code.len()` — the `Bl` relocation, `MovwSym`,
`MovtSym`, and `LdrSym`'s `ldr_offset` — and all four were captured BEFORE the
island block that inserts bytes at that position.

```
INV1  R_ARM_THM_CALL@0x1014 sym=func_0 -> hw1=0xe002 is not a BL
      0xe002 is the island's own `b.n +8`. The real BL sits at 0x101c, still
      `f7ff fffe` — an unpatched `bl .`, i.e. lockup.
INV2  LDR.W lit@0x1010 imm12=0 -> 0x1014 carries no relocation
      the imm12 patch landed at 0x1008, INSIDE the island; the LDR loads CODE
```

Both rc=0 on shapes v0.71 refused loudly — **the same trade the fix existed to
undo, committed inside that fix.**

Red-first, same fixtures and checker:

```
pre-fix  (main's order) : objects checked 2, clean 0, violations 2
post-fix                : objects checked 2, clean 2, violations 0
```

Fixed by ORDERING, made structural: encode and the island decision run ahead of
every recording site, and this instruction's own `LdrSym` is pushed BELOW the
decision, so "a pool can never precede the LDR it serves" stops being a
distance argument.

**The oracle the first fix owed** is now committed:
`island_offset_invariant_345.py` reads both invariants off the EMITTED ELF —
deliberately, because a checker consulting the bookkeeping that was wrong would
agree with it. Corpus-wide: **304 objects checked, 304 clean, 0 violations**.

Its own first CI run went RED at `objects checked: 0` — `ROOT` took two
dirnames instead of three, and the local run had passed the glob explicitly so
the default was never exercised. Both anti-vacuity guards caught it (the
in-script `checked == 0` and the `# ci-checks:` floor). Re-verified with CI's
exact invocation afterwards.

## A SECOND RELEASE-TIME HAZARD IN THE SAME LANE

unreachable it printed `0 advisory/ies` at rc=0. `ci.yml` runs a separate

would have published and cosigned a VEX asserting no advisories. Now refuses,
proven with a stubbed cargo, plus a floor derived from `deny.toml` itself.

## THE ORDINAL, AND WHERE IT CAME FROM

RQ-72-ARCHMODEL claimed **SIXTH** twice and **SEVENTH** twice — two different
wrong values in one file, in the artifact whose own prose warns that "asserting
an ordinal is how it goes wrong". The chain, WALKED:

```
RQ-72 -> RQ-71 -> RQ-70 -> RQ-69 -> RQ-68 -> RQ-67 -> RQ-66 -> RQ-65
      -> RQ-64 -> RQ-63        LENGTH 10
```

The release brief itself says "this will be the SEVENTH consecutive N/A", so
the wrong number arrived with the brief and the artifact inherited it. The
brief's own rule — *"WALK IT, do not carry the number"* — is what caught it.
`_release.yaml` had said "Tenth" all along.
