### The one that matters most: what "caught" means in the headline

The arithmetic is right. From the ledger, re-derived: 38 sampled = 6
uncompilable + 32 compiled; 32 = 11 byte-identical + 21 byte-changing;
21 = 17 killed + 4 untested; 17 = 6 `execution` + 8 `structure` + 2
`freeze-only` + 1 `timeout`; 4 / 21 = 19.0 %. The per-region table
reproduces cell for cell. The candidate pool sums to 1,538. The L1 baseline
timings sum to 23.3 s with `l1_red_on_baseline = []`. The harness at the
survey commit (`ad52535a`, which differs from the document's `580d53f9` only
in `ci.yml` and `mutation_survey.py` — the compiler under test is the same)
already rewrote bare `python` to `python3`, and every recorded kill carries
genuine oracle output (`ORACLE-EVIDENCE … measured=N`), so the "any non-zero
exit is a kill" rule did **not** manufacture kills here.

What the rule *did* do is fold two different events into "killed by an
execution differential". Reading the six `execution` kills' recorded tails:

| mutant | what the killer actually saw |
|---|---|
| `optimizer_bridge.rs:4108:0` | **value mismatch** — `108/117 vectors match wasmtime`, `CHECKS=325/335` |
| `optimizer_bridge.rs:5652:0` | **value mismatch** — `BUG cmp_i64_lt_s(-1,0): want=1 got=0` |
| `select_with_stack.rs:884:0` | 425 modules **newly declined**; the #989 fixtures refused via `#952` → `VACUOUS — declared floor emulations >= 344, measured 0` |
| `select_with_stack.rs:188:45` | 156 newly declined + 141 changed; `#952: 1 of 13 requested export(s) were skipped` → `VACUOUS … measured 96` |
| `optimizer_bridge.rs:3658:0` | the mutated compiler **panicked** (`index out of bounds: the len is 4 but the index is 4`) → `VACUOUS … measured 48` |
| `select_with_stack.rs:5979:0` | 9 modules newly declined → `FAIL PHASE A NEW DECLINE: i64_globals_643.wat is not on EXPECTED_DECLINES` (the census half of the corpus sweep) |

All six make CI red, so `KILLED` is correct. But the release's reading —
"6 by execution differentials … the corpus-sweep oracle is doing the work" —
is not: a differential compared a wrong value in **two** cases. In the other
four the mutant made the compiler refuse or crash, and what noticed was the
`oracle_run.py` non-vacuity floor (the #1112 pattern), the `#952` skipped-
export refusal and the sweep's expected-declines list. That is good news of a
different kind — the loud-decline machinery is load-bearing — and it should
be said, because "the differential caught it" and "the compiler refused and a
floor noticed" are different oracles with different blind spots.

The same distinction changes the headline's frame. Classifying the 21
byte-changing mutants by the ledger's own `changed[].kind`:

| population | n | survived | killed by execution differential (value) | killed by `cargo test` (structure / freeze-only) | killed by floors / census / hang |
|---|---|---|---|---|---|
| changed bytes **silently** (every changed object is `kind: bytes`) | **15** | **4 (27 %)** | 2 | 7 + 2 | 0 |
| loud (≥1 module `newly-declined` or `compile-timeout`) | 6 | 0 | 0 | 1 (`arm_backend.rs:1006:8`: 103 changed, 1 declined) | 5 |

"19 % survive, 81 % are caught" is true as worded — for *CI goes red*. For
the question the survey poses ("what fraction of decisions would an oracle
notice being **wrong**"), the loud six are not wrong code that an oracle
noticed; they are code the compiler refused. On the silent 15 the survival
is 27 % (25 % if `1006:8` is counted silent), and the execution-oracle layer
— the layer the survey was built to measure — caught **2 of 15**; 9 of the
11 silent kills came from `cargo test`, and 2 of those from byte goldens
alone. Neither frame is dishonest; the release states only one.

### FALSE: how control 3 died

`docs/status/MUTATION_SURVEY.md` § "Red-first controls" says of
`CONTROL/startup-r10-seeded-into-r9`: "caught only by the unit tests that
decode the emitted `MOVW`/`MOVT`", and its table cell reads `structure:
cargo test only (274 s)`. The ledger's record for that control:

```
"killed_by": {"layer": "freeze-only", "job": "test", "step": "cargo test",
  "tests": ["?::base_cse_escape_hatch_restores_old_bytes_468",
            "?::const_cse_escape_hatch_restores_old_bytes_242",
            "?::const_cse_default_matches_flip_golden_242"],
  "binaries": ["base_cse_flip_468", "const_cse_reduction_242"], "seconds": 240.9}
```

Three frozen-byte goldens; **no** startup unit test fired. The same unit tests
(`test_minimal_startup_generation`, `test_startup_low_layout_shifted_bases_687`,
…) *did* fire on the neighbouring R11-seed and R9-seed mutants (`main.rs:9340`,
`main.rs:9365`), so the sharper fact is: **the startup's R10 (memory-size)
seed has no unit test at all** — it is protected by change detectors only.
The CHANGELOG ("the third only by frozen-byte goldens") is correct; the survey
document contradicts both the CHANGELOG and its own harness's classification.

### WRONG: the ledger's sampling parameter

`meta.per_region` is `12`; the document says "target 8 compiled per region"
and gives the re-run recipe `run --seed 1189 --per-region 8`. I drew both
orders with the shipped harness on this tree. The ledger's 38 mutants match
the `--per-region 8` draw at all 38 (region, operator) positions (30 of 38
identical by source text as well); the `--per-region 12` draw matches 14 of
38. The RNG is shared across regions inside `sample_sites`, so `per_region`
changes every region's draw after the first. Cause: `cmd_run` executes
`ledger["meta"].update(seed=…, per_region=args.per_region, …)` on every
invocation, and `--per-region` defaults to 12 — a later `run --only …`
overwrote the parameter the survey was actually drawn with. The document's
"the ledger records the seed so a re-run is a comparison, not a new claim" is
true of the seed and false of the ledger as shipped. Fix: `per_region: 8`,
and do not let `--only` runs rewrite `meta`.

### Potency gap: the discrimination job cannot tell a dead oracle from a live one

`cmd_ci` builds the mutant, compiles the corpus, then runs the recorded killer
step and sets `verdict = "KILLED" if code != 0 else "SURVIVED"` (for the
`cargo test` control, `"SURVIVED" if green else "KILLED"`). It never runs the
killer step on the **unmutated** binary in the same environment. An
environment in which the step cannot run at all therefore "kills" every
control and the job prints `failures=0`. I hit exactly that shape on this
machine: the control-2 killer (`cmp_select_two_move_differential.py`) ignores
`$SYNTH` and hard-codes `./target/debug/synth`; before the harness's
`ensure_symlink()` had created that path it exited 1 with
`FileNotFoundError` in 0 s on the *unmutated* binary — a "kill" of nothing.
With the symlink in place it is green (`11/11 match … ORACLE: PASS`), as are
the control-1 killer (`149 matched, 0 diverged, RESULT: PASS`) and the #989
differential (`CHECKS=340/340`). The `run`/`controls` path records
`l1_red_on_baseline` and so has this protection; `ci` does not. Cheapest fix:
run each `ci_subset` killer step once on the baseline before mutating and
refuse (`VACUOUS`) if it is not green.

**Replay result on this machine** (`CARGO_TARGET_DIR=target-review python3
scripts/mutation_survey.py ci`): `MUTANTS-CI subset=7 controls=3
non-killed=4 failures=0`. The portable half — byte triage — reproduces
exactly: `optimizer_bridge.rs:6705:0` → 8 changed objects, `liveness.rs:
7025:36` → 53 (the post-drift figure the survey document declares), `arm_
backend.rs:1565:21` EQUIVALENT, `arm_backend.rs:1316:36` DEAD, against a
live baseline that differs from the ledger's on 13 of 609 entries (the
document's figure). The non-portable half — the three controls coming back
`KILLED` in 14 s / 14 s / 254 s — is admissible **only** because this review
first ran each recorded killer green on the *unmutated* binary in the same
environment: `join_alias_1189_differential.py` `RESULT: PASS` (223
emulations), `cmp_select_two_move_differential.py` `ORACLE: PASS` (22
emulations, after the symlink), and `cargo test --workspace` (69 test
binaries, 1,714 tests, 0 failed). This machine has no bare `python`; the
harness's `_subst` rewrote the steps to `python3` and the oracle output
above shows they executed. A kill scored in this environment without that
baseline would not have been evidence, which is the gap.
