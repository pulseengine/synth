### SHOULD-FIX 1 — the cited `.wast` mis-binding instance (`four` → "a local body in module 1 or 2") did not happen on v0.62.0; the CHANGELOG promotes the new refusal's *hypothetical* to an *observation*

- **Claim as written** (`CHANGELOG.md:68-71`): "A `.wast` merge bound a call to the wrong module's body. `four` (module 0) calling import 0 silently resolved to a local body in module 1 or 2, because the merge shares one `func_N` label space. Exit 0, wrong function called."
- **What I did:** `four` is the export in `tests/spec-testsuite/func_ptrs.wast:24` (three modules; module 0 imports `spectest.print_i32` and `four` calls it). I compiled that file with the **shipped v0.62.0 binary** on every leg that emits an object — `cortex-m3 --relocatable`, `-b arm` (A32, no target), `rv32imac --relocatable`, and the self-contained `--cortex-m` leg the spec census uses — with and without `--allow-skipped-exports`, and read the relocation on `four`'s call.
- **What I found:** on every leg, `four`'s call carries a relocation against the **import symbol**, not a `func_N` label: `R_ARM_THM_CALL print_i32`, `R_ARM_CALL print_i32`, `R_RISCV_CALL_PLT print_i32`. Modules 1 and 2 of that file contribute nothing to the object (their exports `callt`/`callu` decline on `call_indirect`), so there is no local body the call could have bound to. Exit 0, **correct** symbol. The HEAD refusal (`crates/synth-cli/src/main.rs:3241`, `:3207`) itself says "`func_0` **would** bind to a local body" — the CHANGELOG restates that conditional as a measured miscompile ("silently resolved … wrong function called"). aarch64 refuses this file on v0.62.0 anyway (`#851`).
- **What IS true:** the mis-binding **class** is real for local-vs-local label collisions. I extracted `LABEL_COLLISION_WAST` from `crates/synth-cli/tests/wast_callgraph_closure_1168.rs` (module 0 `f`+`g`, module 1 `h`; `g` calls index 0) and compiled it on v0.62.0: exit 0, object written, symtab carries **two local `func_0` symbols** (`0x0 = h`, `0x8 = f`) and `g`'s `bl` relocates against `func_0` — an ambiguous binding a linker resolves arbitrarily. HEAD refuses it with `#1168` and writes no object. The artifact (`RQ-63-WASTCLOSURE.yaml`, half (a)) describes exactly this local-label case; the CHANGELOG swapped in the `four`/import instance, which is the one the new check over-refuses conservatively rather than one that was ever mis-bound.
- **Fix:** replace the example with the local-label collision (`g` → `f`/`h`), or say "would have bound" and that the import case is refused conservatively. Also worth recording as a reach cost: `func_ptrs.wast` now declines on arm/rv32 for a mis-bind that the emitted relocation shows cannot occur for an import call.
- **Evidence:** scratch objects `t/tfour/{v062,a32,rv32,selfc}.o` (relocation listings above); `t/tcoll/v062.o` symtab; `main.rs:3200-3245`; artifact `RQ-63-WASTCLOSURE.yaml` description (a).

### SHOULD-FIX 2 — the `+no-optimize` ladder rung *cannot* move: `--no-optimize` is a no-op under the ladder's own `--relocatable` base invocation on all three backends, so the published "negative result" is a tautology and the inference drawn from it is unsupported

- **Claim as written:** `CHANGELOG.md:36-37` "`--no-optimize` adds **zero** on every backend." `docs/status/ACCEPTANCE_LADDER.md:25-26`: "adds zero on every backend, which is worth knowing in itself: **the two selector paths differ in output, not in acceptance**." Worth publishing as a negative result.").
- **What I did:** read every consumer of `CompileConfig::no_optimize` (`grep -rn no_optimize crates/ --include='*.rs'`, excluding the CLI pass-through) and the ladder's invocation.
- **What I found:**
  - The ladder's *every* rung runs `--all-exports --relocatable` (`scripts/repro/partial_census_1017.py:187-195`, `LADDER_RUNGS` at `:642-649`).
  - The **only** consumer of `no_optimize` outside the CLI is the ARM selector choice, `crates/synth-backend/src/arm_backend.rs:990-991`: `if config.no_optimize || config.relocatable || …` → direct selector. Under `--relocatable` the direct selector is already forced (#197, `main.rs:4240`), so `--no-optimize` changes nothing on ARM.
  - `synth-backend-riscv` and `synth-backend-aarch64` **never read** `no_optimize` at all (each has one selector).
  - Therefore the fourth rung is structurally identical to the third on every backend; "+0" is the only value it can ever report. The optimized ARM selector was **never invoked** by the ladder, so no statement about "the two selector paths" follows from it.
- **Why it matters:** this is the release's own "checker that cannot fail" class, in the measurement harness rather than a CI gate — a rung that reports a number no input can change. The CHANGELOG sentence is literally true; the doc/artifact inference it is presented as supporting is not measured. (The `_release.yaml` sample table reports the same `+no-opt 0` on 60 modules for the same reason.)
- **Fix:** either drop the rung, or make it meaningful by running it *without* `--relocatable` (which changes the ABI and is a different measurement) — and delete the "selector paths differ in output, not in acceptance" sentence from the doc and the two artifacts, or re-derive it from a run that actually reaches the optimized selector.
- **Evidence:** `arm_backend.rs:990-1001`; `partial_census_1017.py:187-195, 642-649`; grep of `no_optimize` across `crates/` (only `arm_backend.rs` + `synth-core/src/backend.rs:104`).
