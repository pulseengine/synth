### 1. ISLANDS deferred a MUST on a blocker that does not exist

The artifact said *"There is NO post-encode branch relaxation or fixup pass"*,
citing `grep -nE 'fn [a-z_]*(relax|fixup|patch)'`.

That command prints **nothing at all** (rc=1) — here and at `23c6b2d2` where the
artifact landed — so it could not "find only literal-pool patching". An empty
result over a guessed name pattern is not evidence of absence, and it missed the
function that refutes the claim:

```
resolve_label_branches   arm_backend.rs:2333, called at 1468 and 1590
"Sizes only grow (16->32-bit), so this converges quickly; cap for safety."
```

That **is** a branch-relaxation pass with a size fixed point, and it runs on the
DIRECT selector — exactly the `--relocatable` path the lane is about (#197).
What genuinely has no post-encode fixup is the OPTIMIZED path's inline
`BOffset`/`BCondOffset`, which carry no label.

**Corrected.** The deferral stands — a constant-island pass is real work and
v0.71 had no capacity after the two musts — but it is deferred for **size**, not
for an absent mechanism. The false sentence had also shipped into
`scripts/repro/litpool_islands_345.py`; both copies are fixed.

### 2. A gate this release built could not pass

`musl-portable-asset` (and the same step in `release.yml`) asserted
`file "$BIN" | grep -q 'statically linked'`. rustc's musl target never emits
that string: its spec sets `crt-static-default` **and**
`static-position-independent-executables`, so the link is `-static-pie` and
`file` reports `static-pie linked`.

The gate would have **refused a correct artifact** — and `create-release` has
`needs: [build-binaries]`, so that is not one missing archive, it is **no
release at all**. A gate that cannot pass, in the workflow that publishes the
release, in the lane whose whole point is that the asset is checkable.

**Corrected** to read the property from the ELF (`no PT_INTERP`) rather than
`file`'s wording, validated both ways before shipping: it refuses the real
published v0.70.0 gnu asset (`PT_INTERP=1`, 17 `GLIBC_` occurrences, rc=1) and
accepts a synthesised static-pie shape (rc=0). The potency control was widened
at the same time — the gnu leg now runs the **same** check and must fail it, so
both assertions have a negative control.

### 3. STACKDEPTH carried a false mechanism, duplicated into its oracle

*"the optimized path's prologue costs 8 more bytes per frame."*

Re-measured from both sidecars on one tree: `8/64/120` against `16/72/128`. The
delta is a **constant +8 arising in the zero-frame leaf** (`func_0`: 8 → 16),
propagating once. Were it per-frame, `top` — three frames in its chain — would
differ by more than 8; it differs by exactly 8. Non-leaf own-frames are 56 in
**both** modes. The conclusion it supported (the number is a property of the
build you ship) is unaffected.

## A FOURTH tag-blocker, found at the cut: the release that shipped `issue-scope: outlives` had two artifacts needing it and set neither

Found at the cut, while deriving the close-set rather than recalling it. The

      AUTHORISED: {1250: ISSUESCOPE, 1341: STACKDEPTH, 1349: MUSL, 1354: VFPALIAS}

**`held_open` was empty in the release that introduced the field.** RQ-71-ISSUESCOPE
(#1250) exists because "no existing field separates the close-set from the
keep-open set". It shipped the vocabulary, the R12 rule, the gate and 17 unit
assertions — and then the two artifacts that needed it did not use it, so the
default would have closed both issues on the tag.

Both were confirmed against the issues themselves, not against the artifacts'
own prose:

- **#1341 (cpetig) — `--emit-stack-depth`.** The issue asks for THREE things;
  the artifact says "Deliver items 1/2, not 3". Item 3 is a stack line in
  `docs/embedder-abi-relocatable-arm.md` under "Region requirements".
  `git diff --stat v0.70.0..HEAD -- docs/embedder-abi-relocatable-arm.md` is
  EMPTY and the file has zero occurrences of `stack depth`, `synth-stack-v1` or
  `--emit-stack-depth`. So the consumer-facing ABI document does not mention the
  number this release built for that consumer — under the theme "The number the
  consumer needs", the number shipped and the place they would look for it did
  not. cpetig wrote that even *"the embedder must size this itself, synth does
  not bound it"* would have saved the investigation.
- **#1349 — musl assets.** The issue names TWO triples explicitly,
  `x86_64-unknown-linux-musl` **and** `aarch64-unknown-linux-musl`. The release
  matrix gained only the first. An arm64 Alpine / `distroless-static` consumer —
  the case the issue was filed from — is still unserved.

Closing either on the v0.71 tag would have been the v0.69 class again: an
external reporter's live issue closed by this loop's own machinery while the
thing they asked for was still missing. Both now carry `issue-scope: outlives`
with the measurement in the field, the derived close-set is `{1250, 1354}`, and
`held_open` is `{1341, 1349}`.

**The mechanism failure worth keeping.** The first attempt at this edit placed
`issue-scope:` at the artifact's TOP LEVEL, guarded by `assert count(anchor)==1`,
and the assert passed — `status: implemented` really did occur exactly once. But
these artifacts nest the checked keys under a literal `fields:` map, so the new
key landed where nothing reads it. `status_evidence` stayed rc=0 and the census
printed no change, because an unread key is indistinguishable from an absent
one. Only re-deriving `authorised_close_set` caught it:

    HELD OPEN: {}          <- after the "successful" edit

A uniqueness assert guards against editing the WRONG TEXT. It does not guard
against editing the wrong PARENT. The check that discriminates is the one that
re-derives the value the edit was supposed to change — see
[[feedback_index_picks_the_wrong_match]] for the sibling class.

## The plan promised 6 mechanical done-when; the tag ships 5 — measured

`loop_conformance_check` step 3 reports **8/8 done-when DECLARED — 5
mechanically evaluable, 3 manual**. The v0.71 plan said six. The missing one is
RQ-71-MUTANTDRIFT, whose planned predicate was
`contains:.github/workflows/ci.yml:reanchor`.

This was checked rather than explained away. Temporarily restoring that
predicate on the cut tree:

    FAIL R3 RQ-71-MUTANTDRIFT: status `proposed` but its done-when evidence
    EXISTS on this tree (contains:.github/workflows/ci.yml:reanchor) —
    the status under-reports shipped work
    status_evidence rc=1

So the ratio is **forced, not a degradation**. MUTANTDRIFT was REFUTED: the
drift it proposed to fix turns out to be already named, with its remedy, by the
existing anchor. A refuted artifact keeps `status: proposed` +
`disposition: refuted` (R11 forbids pairing `disposition:` with a CLAIMING
status), and a mechanical predicate that evaluates TRUE beside a non-claiming
status is exactly what R3 exists to catch. The two rules together make
"refuted" and "mechanically evaluable" mutually exclusive by construction.

The general form, worth keeping: **a lane that ends in a refutation cannot
contribute to a mechanical-done-when ratio**, so that ratio is only comparable
across releases with the same number of refutations. Planning six and shipping
five is what a plan that leaves room to be wrong looks like. (The file was
restored and `git diff --quiet` confirmed clean before the cut.)
