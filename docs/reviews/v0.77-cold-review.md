**Commit reviewed:** `265a1256`, the head of the release PR #1429, in two isolated
worktrees with submodules initialized (`tests/spec-testsuite` — an empty suite
makes the corpus audits vacuous).

Round 1 ran two fresh-context passes with no inherited framing: **PROSE-TRUTH**
(falsify every checkable claim, plus the external-reporter conduct question) and
**GATE-POTENCY** (make each gate this release added go red, or report that it

**Headline:** round 1 examined 78 checkable statements and found **9 false**, 2
misleading, 3 under-specified. Zero of the seven gates was vacuous — every one can
be made to go red — but the release's **flagship number was a true count of a
narrower population**, and one false sentence had been reproduced into an issue

## Round 1, pass B — GATE-POTENCY. Seven gates, zero vacuous

Every mutation confirmed applied with `git diff --numstat` and restored from a `cp`
backup. Twelve distinct mutations. **All seven gates can be made to go red.**

### B1 — SEVERE: the new `GateRefusal` handler had NO committed coverage (FIXED)

The refusal *mechanism* is potent — measured working. What was absent is any test
that would notice it regressing, and the uncovered half is load-bearing:

| mutation | numstat | `--self-test` | callsite driver | live |
|---|---|---|---|---|
| `print(f"GATEREFUSED {why}")` → `print("GATEOK")`, `return 2` intact | `1 1` | rc=0 | rc=0 | rc=2 but `grep -c '^GATEOK$'` = **1** |

`merge_ritual.sh` gated the merge **solely** on `grep -q '^GATEOK$'` and discarded
the exit code, so that one string change made a zero-check or wrong-head rollup
**merge** while both CI instruments stayed green. `GATEREFUSED` appeared in three
places in the tree — the emitting line, the CHANGELOG, and an artifact — and **no
test asserted it**.

**Fixed:** four refusal scenarios added to `test_merge_gate_callsite.py`, asserting
the string and the code separately, plus a positive control that the head the
caller *did* ask about still passes.

### B2 — a shipped docstring made a false statement about this tree (FIXED)

`merge_gate.py`'s `fidelity_exit` docstring said the call site "is still untested"
and a real fix "is a v0.75 candidate and is NOT claimed here". v0.75 delivered it,

exactly the named mutation with three failures. Read the state of a gap before
describing it — and the shape recurred anyway, one level in: v0.77 added a branch
to that already-covered function without extending its driver.

### B3 — an empty `--expect-head` silently disabled the subject check (FIXED)

`subject_refusal(72, head, "")` returned `None`, and end-to-end an empty expectation
printed `GATEOK` rc=0 with no diagnostic. `merge_ritual.sh` computes it with
`EXPECT=$(git rev-parse ...)` under `set -uo pipefail` **without `-e`**, so a git
failing at the repo level leaves it empty and execution continues.

**Fixed:** an expectation that derived to the empty string is now a **refusal**,
not a no-op — this release's own rule applied to the gate's own input — with
`expect_head=None` still a documented no-op, pinned by three new self-test
assertions.

### B4 — the only caller discarded the exit code, falsifying the artifact's premise (FIXED)

`GateRefusal`'s docstring says exit 2 exists so "a caller must be able to tell 'the

**Fixed:** the ritual redirects, captures `GATERC`, and exits 2 on a refusal with a

### B5 — the `--verify` conclusion was a string literal (FIXED)

### B6 — four of seven new `oracle_run` tests pass on the real parent (DISCLOSED)

## C4 — running the close-set gate at the cut found a gate CONTRADICTION (filed #1430)

The brief requires deriving the close set before the tag with
`issue_closure_check.py --allow-unclosed` while the PR is still amendable. Doing so
produced three results:

**The prior-release attribution still fires** (the brief asked this be verified):
#1255, #1257 and #1404 report as `ATTRIBUTED TO v0.76` rather than "closed but not
authorised", whose old remedy was to reopen correctly-closed issues.

**The gate authorised four issues; two are now held open explicitly.** The gate said
#1319, #1403, #1418 and #1419 were all authorised. Independent verification of each
issue's ASKS disagreed for two, so `issue-scope: outlives` is now set on
RQ-77-SUBJECT (#1418) and RQ-77-CENSUS (#1403) with the measured reason inline. The
close set is now **2 authorised, 3 held open**, matching the coordinator's
derivation exactly.

**And one FAIL that cannot be fixed without making another gate red.** #1243 is
closed, correctly, citing v0.66.0 where the fix shipped. `issue_closure_check` calls
that "CLOSED BUT NOT AUTHORISED" and prescribes either reopening it or naming it in
a delivering artifact. Flipping RQ-77-FLOORREGEX to a claiming status to do the
latter makes `status_evidence` R11 refuse — *"status `implemented` claims the outcome
holds but `disposition: refuted` says it does not — pick one"* — and **R11 is
right**.

The cause was checked rather than guessed. The first hypothesis was that attribution
looks only one release back; its docstring says the opposite, explicitly. The real
reason is that **#1243 was filed AFTER v0.66.0 shipped the fix**, so no artifact
anywhere could name it — a third category the gate does not represent, and the normal
shape of "a fix shipped without closing its issue", which v0.77 hit **twice**
(#1243 and #1319) as dead `must` premises.

**Disposition: #1243 stays closed and the gate stays red**, documented inline in the
artifact and filed as #1430. The gate is advisory at the tag by its own design.
Reopening a fixed issue to green a gate is the wrong direction, and leaving #1243
open is what let this release scope a dead premise as a `must` in the first place.
