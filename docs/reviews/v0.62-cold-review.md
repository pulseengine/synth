### SHOULD-FIX 1 — the constant-index "devirtualizes" claim is false, and the compiler's own bytes refute it

- **Claim as written** (CHANGELOG lines 77–79, `0a8c1e1f`): "The dynamic index is load-bearing; a constant index devirtualizes and the table never materializes." Repeated in `artifacts/release-v0.62/RQ-62-TABLEDANGLE.yaml` (~line 68: "with `i32.const 0` the ARM relocatable path devirtualizes the dispatch into a direct call and the table never materializes") and `crates/synth-cli/tests/tabledangle_1102_elem.rs:13`.
- **What I did:** compiled the artifact's exact fixture shape with `i32.const 0` as the index (`(table 2 funcref)`, `(elem ...)`, `call_indirect (type $t)`) on `thumbv7m-none-eabi --relocatable --all-exports` at HEAD, and disassembled the object. No compiler source changed after the fix commit, so HEAD's selector is the same code the claim describes.
- **What I found:** the emitted dispatch is `ldr.w r12, [r11, r12]` + `blx r12` — a **runtime table load through the R11 region, identical to the dynamic-index case**. No direct call is emitted; the table dispatch absolutely materializes. I found no devirtualization code anywhere (`grep -rn devirt crates/` matches only comments repeating this claim). The ARM `CallIndirect` lowering (`select_with_stack.rs:4672`) unconditionally goes through the table.
- **Why it matters:** (1) it is a factual error in the release prose, the artifact, and a test's doc comment — three copies of the same wrong sentence; (2) it undermines the artifact's "why this wasn't found earlier" narrative (a const-index fixture would NOT have reported "no bug" for the reason stated); (3) there is **no live hole** — I verified the gate is index-insensitive: a const-index module naming a declined function IS refused at HEAD (`#1102/RQ-62-TABLEDANGLE` fired on my `i32.const 0` fixture). Prose fix only.
- **Evidence:** fixture + disasm reproduced twice (with and without a `(type $t)` declaration); `crates/synth-synthesis/src/instruction_selector/select_with_stack.rs:4672` (no const-index path); `crates/synth-cli/src/main.rs:4598-4606` (gate matches any `CallIndirect`, index-insensitive).

This is recorded as a note, not a finding, because it was found and fixed by the release's own process — but it is the reviewed commit's one numeric claim that over-promised at the time it was written.

### NOTE 3 — the 81% → 11% causal subcounts are corroborated, not re-derivable

- **Claim:** "The 81% (v0.59, same stratum) counted 125 partial objects and 77 accepts that were silently dropping active data segments... The rate fell because we stopped lying."
- **What I did:** searched for a contemporaneous record. `artifacts/release-v0.59.yaml:611-648` (written at v0.59, not by this release) records: 307 modules, 249/307 accepts (=81.1%), "125 of 307 modules (41%) are ACCEPT_INTERNAL_SKIPS", "77 of 249 accepts carry active data segments that ARM --relocatable currently DROPS silently (#1041)". Both subcounts match, from a record that predates this release.
- **What cannot be verified:** the per-module records of the v0.59 run were not preserved (the REACH artifact says so itself), the corpus snapshot moved (307 → 243), and the overlap between the 125 and the 77 is unquantifiable — so the decomposition of the fall cannot be exactly recomputed. Directionally the story holds and the current partial bucket **is** zero (verified by re-run, below); the residual honest-accept pools are of comparable size (249−125−77=47/307 ≈ 15% vs 27/243 = 11%). Also: "same stratum" is true (org-repos-on-this-machine) but the CHANGELOG omits that the denominator differs (307 vs 243) — the artifact states it, the CHANGELOG does not.

### NOTE 4 — "fail-closed on unknown mnemonics" is narrower than it reads

- **Claim:** `synth verify-embedder` is "fail-closed on unknown mnemonics".
- **What I found:** an unknown mnemonic refuses **only when its text names a reserved register**; an unknown mnemonic not mentioning R9/R10/R11 passes (deliberately, per the unit test `unknown_mnemonic_without_reserved_passes`, `crates/synth-cli/src/verify_embedder.rs:935`). Undecodable bytes in an executable region always refuse (`:605`), and a 0-instruction scan always refuses (`:737`). Reasonable engineering, but the CHANGELOG sentence claims slightly more than the code does. Also, the "warning when the scan finds zero writes" is a stdout `note:` (`:782`) that fires only when no `--allow-writer` was given — present, as claimed.

### NOTE 5 — census blocker-bucket collapsing leaks instance payloads for one class

- The census claims "Instance-specific payloads ... are collapsed so one CAUSE is one bucket", yet my arm re-run shows `encode_operand2: immediate 0x624 ...` (4) and `... 0x5dc ...` (1) as **separate** buckets — the hex immediate is not masked by the `N`-collapse. The artifact's "5 encode_operand2" total is the correct sum, so no number in the release is wrong; the script's collapse just doesn't fully deliver its stated property. Cosmetic.

## Verdict

The release's numbers are, with the exceptions above, **honest and reproducible**: the census table reproduces exactly from a fresh binary; the ratchet, proof-count, and oracle-floor claims equal their live derivations; the headline #1102-residual hole is real (reproduced on the pre-fix compiler through to a clean link with zero UNDEF symbols) and really closed on every host-linked path; the #1145 story checks out at the level of emitted symbols and decline text. The two things to fix before the tag: attribute `b9450a66` so the tip passes its own status-evidence gate (MUST-FIX 1), and strike or correct the three copies of the false "constant index devirtualizes" sentence (SHOULD-FIX 1) — the exact same-author-prose class this review exists to catch, caught this time by disassembling what the compiler actually emits.
